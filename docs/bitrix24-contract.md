# Контракт облачного Bitrix24

Каноническая версия контракта находится в [`api/bitrix24-contract.md`](api/bitrix24-contract.md). Ниже сохранены подробности ранее выполненных живых smoke-проверок.

## Проверенный тестовый контур

12 сентября 2026 года входящий webhook собственного облачного тестового портала успешно выполнил `profile`, `scope` и `methods`. Доступен scope `calendar` и все методы текущего адаптера: `calendar.section.get`, `calendar.section.add`, `calendar.event.get`, `calendar.event.add`, `calendar.event.update`, `calendar.event.delete`.

Для проверки использовался отдельный webhook тестового портала с ограниченными правами календаря и пользователей. URL портала, токен, имя и другие поля профиля в репозиторий не записаны.

В портале проверены три разные учётные записи — владельцы личных календарей. Для каждой создан отдельный раздел `LeaveOps — отсутствия`. Живые smoke-тесты создали синтетические события на 15–16 января 2099 года в двух из этих разделов, нашли их через API, удалили и подтвердили отсутствие повторным чтением. Выделенные разделы сохранены пустыми; старый одиночный тестовый раздел новым адаптером не используется.

## Отображение данных

| LeaveOps | Bitrix24 Calendar |
| --- | --- |
| request.id | метка `[LeaveOps:<id>]` в description |
| employee_id | выбирает owner_id и section_id через runtime-карту; также входит в name |
| start_date / end_date | from / to |
| отсутствие на весь день | skip_time = Y |
| согласованная заявка | calendar.event.add, accessibility = absent |
| согласованный перенос периода | calendar.event.update с тем же external_id |
| отмена | calendar.event.delete |
| external_id | ID события из ответа calendar.event.add |

Даты заявки в LeaveOps включают первый и последний день. Реальный тест подтвердил создание и чтение события с переданным периодом; визуальное отображение границ в интерфейсе Bitrix24 ещё не проверялось.

## Идемпотентность

У `calendar.event.add` нет используемого нами idempotency key. Перед созданием адаптер читает события выделенного раздела за период заявки и ищет служебную метку. Если событие уже существует, возвращает его ID вместо повторного создания. Это покрывает потерю ответа при неизменяемых датах заявки.

При отмене адаптер ищет метку и удаляет найденное событие. Если событие уже отсутствует, отмена считается выполненной и сохраняет известный внешний ID. Очередь LeaveOps хранит попытки, последнюю ошибку и внешний ID отдельно от бизнес-статуса заявки.

При переносе согласованной заявки исходные даты остаются действующими, пока руководитель не примет новое решение. Если первоначальное создание уже доставлено, очередь передаёт известный `external_id` в `calendar.event.update`; повтор обновления изменяет тот же объект. Если создание ещё pending, LeaveOps заменяет его payload новыми датами и не ставит обновление без внешнего ID.

## Ограничения

- Для каждого сопоставленного сотрудника используется отдельный личный раздел `LeaveOps — отсутствия`. На портале проверены три владельца; остальные три синтетических сотрудника намеренно не сопоставлены.
- Webhook-пользователь становится организатором события, даже когда ownerId указывает другого пользователя. Запись в личный раздел другого пользователя подтверждена, но уведомления и участие сотрудника не проверены.
- Входящие события Bitrix24 не используются; внешний сервер и исходящий webhook не нужны для этого одностороннего сценария.
- Перенос одной согласованной заявки поддерживается через повторное решение руководителя и `calendar.event.update`. Массовые переносы, смена владельца календаря и обратная синхронизация не поддерживаются.
- Обработка ограничений частоты и длительных отказов пока использует ручной повтор очереди без фонового расписания.
