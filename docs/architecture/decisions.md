# Архитектурные решения

> ADR реконструированы по существующей реализации и тестам. Они фиксируют наблюдаемые решения для портфельного кейса и не изображаются как документы, утверждённые до разработки.

## ADR-001 — разделить бизнес-статус и доставку

**Статус:** принято, подтверждено реализацией.<br>
**Контекст:** решение по заявке и доступность внешнего календаря имеют разные причины изменения.<br>
**Решение:** хранить бизнес-состояние в `requests.status`, техническое — в `integration_events.status`.<br>
**Альтернативы:** откатывать approval при ошибке API; хранить единый смешанный статус.<br>
**Последствия:** сбой Bitrix24 не отменяет решение; UI должен показывать два состояния.<br>
**Доказательство:** `LeaveOps.transition`, `IntegrationWorker.run_once`, `test_approval_enqueues_event_in_same_transaction`.

## ADR-002 — transactional outbox

**Статус:** принято.<br>
**Контекст:** SQLite и Bitrix24 не поддерживают общую распределённую транзакцию.<br>
**Решение:** записывать `integration_events` в той же локальной транзакции, что заявку и историю; доставлять позже.<br>
**Альтернативы:** прямой вызов API до commit; вызов после commit без устойчивой очереди.<br>
**Последствия:** команда доставки не теряется после бизнес-решения; нужен worker, lease и повторы.<br>
**Доказательство:** `_enqueue`, `_connection(write=True)`, `test_blocked_approval_does_not_enqueue`.

## ADR-003 — повторная проверка правил в транзакции

**Статус:** принято.<br>
**Контекст:** preview может устареть между открытием карточки и решением.<br>
**Решение:** выполнять `_conflicts` после `BEGIN IMMEDIATE` непосредственно перед переходом или изменением дат.<br>
**Альтернативы:** доверять preview; резервировать покрытие при `submitted`.<br>
**Последствия:** конкурирующие решения сериализуются; pending-заявки не резервируют ресурс.<br>
**Доказательство:** `transition`, `decide_reschedule`, `test_concurrent_approvals_cannot_both_pass`.

## ADR-004 — отдельная сущность переноса

**Статус:** принято.<br>
**Контекст:** предложенные даты ещё не являются согласованным отсутствием.<br>
**Решение:** хранить их в `reschedule_proposals`; менять `requests.start_date/end_date` только после approval.<br>
**Альтернативы:** сразу менять заявку с возможным rollback; создавать вторую заявку.<br>
**Последствия:** действующий период остаётся стабильным; отказ не требует восстановления; сервис ограничивает одно открытое предложение.<br>
**Доказательство:** `propose_reschedule`, `decide_reschedule`, `test_reschedule_rejection_preserves_approved_period`.

## ADR-005 — идемпотентность по служебной метке

**Статус:** принято.<br>
**Контекст:** после `calendar.event.add` ответ может потеряться; используемого application idempotency key нет.<br>
**Решение:** добавлять `[LeaveOps:<request_id>]` в `description` и искать его перед `add`.<br>
**Альтернативы:** слепой повтор; полагаться только на локальный `external_id`; создавать собственный gateway.<br>
**Последствия:** неизменный период не дублируется; поиск зависит от периода и раздела, поэтому перенос использует `update`.<br>
**Доказательство:** `_marker`, `_find`, `deliver`, `test_real_adapter_contract_recovers_lost_add_response`.

## ADR-006 — личные разделы Bitrix24

**Статус:** принято для тестового контура.<br>
**Контекст:** событие должно находиться в календаре конкретного пользователя, а webhook принадлежит отдельной учётной записи.<br>
**Решение:** хранить runtime-карту уникальных `owner_id + section_id` и маршрутизировать событие по `employee_id`.<br>
**Альтернативы:** один общий календарь; один раздел webhook-пользователя; участники meeting.<br>
**Последствия:** требуется preflight и локальная конфигурация; webhook-пользователь остаётся организатором, уведомления не доказаны.<br>
**Доказательство:** `MappedBitrix24CalendarAdapter`, `mapping_preflight`, mapping contract tests.

## ADR-007 — SQLite для детерминированного PoC

**Статус:** принято для демонстрации.<br>
**Контекст:** кейсу нужны устойчивость, ограничения, транзакции и конкурентная проверка без инфраструктуры.<br>
**Решение:** использовать отдельные SQLite-файлы для LeaveOps и Mock Bitrix24.<br>
**Альтернативы:** in-memory collections; PostgreSQL; единая база для приложения и mock.<br>
**Последствия:** простой воспроизводимый запуск и реальные транзакции; нет production-масштабирования и HA.<br>
**Доказательство:** `service.py`, `MockBitrix24`, временные базы во всех test suites.

## ADR-008 — отсутствие сторонних runtime-зависимостей

**Статус:** принято для демонстрации.<br>
**Контекст:** портфельный проект должен запускаться на чистом Python с минимальным setup.<br>
**Решение:** HTTP, CLI, SQLite и REST client реализовать standard library.<br>
**Альтернативы:** FastAPI/SQLAlchemy/requests; frontend build chain.<br>
**Последствия:** воспроизводимость выше; локальный HTTP transport и ручная маршрутизация не подходят для production.<br>
**Доказательство:** imports, README quick start, `test_cli_real_process`, 52 tests без установки packages.

## ADR-009 — демонстрационная формула баланса

**Статус:** принято с ограничением.<br>
**Контекст:** production-правила, праздники и кадровый источник отсутствуют.<br>
**Решение:** opening days + начисление по месяцам − календарные дни завершённых и будущих approved-периодов.<br>
**Альтернативы:** исключить баланс; имитировать производственные правила; подключить 1С.<br>
**Последствия:** правило можно проверить end-to-end, но результат нельзя использовать как кадровые данные.<br>
**Доказательство:** `_months`, `_balance`, `balance-rules.md`, workflow/web balance tests.
