# План выявления и проверки требований

> Это реконструированный план выявления требований для портфельного кейса. Он показывает, как следовало бы валидировать модель с реальными участниками; фактическое проведение интервью не заявляется.

| Метод | Цель | Участники / источники | Ожидаемый результат |
| --- | --- | --- | --- |
| Интервью | Уточнить критерии решения, ответственность и исключения | Сотрудник, руководитель, HR, администратор интеграции | Термины, ожидания, исключения, список открытых вопросов |
| Process walkthrough | Восстановить последовательность AS-IS и точки передачи данных | Руководитель, HR, сотрудник | BPMN AS-IS, болевые точки, ручные операции |
| Анализ документов | Проверить правила баланса, календаря и полномочий | Внутренние регламенты, календарь, кадровые правила | Подтверждённые правила и ограничения; в демо источники отсутствуют |
| Анализ интерфейсов | Отделить бизнес-статус от технической доставки | `leaveops/web.py`, UI, CLI | Акторы, команды, ошибки и границы доступа |
| Анализ данных | Подтвердить сущности, статусы и инварианты | SQLite DDL в `leaveops/service.py` | Логическая и физическая модели |
| Анализ API | Проверить контракт интеграции и возможные отказы | `leaveops/integration.py`, документация Bitrix24, тестовый портал | Маппинг, идемпотентность, обработка ошибок |
| Обзор прототипа | Проверить понятность сценария и результата | Представители ролей на синтетических данных | Замечания к Use Case и acceptance criteria |
| Scenario validation | Проверить позитивные и негативные ветви | Decision tables, automated tests | Согласованные ожидаемые исходы и набор проверок |
| Requirements review | Найти противоречия и пропуски | Владелец системы и ключевые стороны | Версионированный набор BR/RULE/FR/NFR и решения по OQ |

## Последовательность

1. Зафиксировать проблему, границы и термины.
2. Провести walkthrough AS-IS и связать наблюдения с `PP-xxx`.
3. Сформировать outcome-oriented `BR-xx`.
4. Валидировать правила через decision tables и Use Case.
5. Сверить данные, API и интеграционные отказы с реализацией.
6. Провести обзор TO-BE, прототипа и acceptance criteria.
7. Перевести нерешённые вопросы в решения, backlog или production constraints.
